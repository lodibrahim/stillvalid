| 2026-09-27 | Path matching: the exact repo path, the path without a diff's `a/`/`b/` prefix, or, for **absolute** paths only, the one file at base ending in its longest suffix of >= 2 components; relative paths get no suffix match. | 2026-09-27 | **Renames are followed**, not counted: when a path is gone at head, the last first-parent commit in base..head that deleted it is checked with git's rename detection (`-M`, 50%); a move continues from the new path (up to 10 hops). Only a real delete counts; evidence is the deleting `commit` ("Deleted X (named in the issue)" or "Renamed X -> Y, then deleted") | 6 of 7 ripgrep hits were the 2020 `src/` → `crates/` move, not code going away | Count renames as gone; `git log --follow` (walks backwards only) |
| 2026-09-27 | "Heavily rewritten" = the file (after renames) still exists, had >= 20 lines at base, and >= 75% of those lines are deleted or changed at head (`git diff --numstat base:old head:new`); evidence is a `code` item with the head path and "N% of its lines changed since the issue was filed (at <base>)" | ripgrep: only `crates/regex/src/literal.rs` (80%) qualifies; next highest code file was 25% | 50% threshold; per-line `git blame --reverse` |
| 2026-09-27 | Symbols: the last `::`/`.` segment, >= 4 chars, whole-word fixed-string `git grep -w`; error strings: fixed-string, case-sensitive, >= 20 chars. | 2026-09-27 | The code check runs **only when the reference check found nothing** (closing PR/commit wins; no merged evidence). | 2026-09-27 | PR merge checks cost: one batched `git fetch --no-write-fetch-head origin <sha>...` by the API's PR head SHAs (no local refs; one fetch per SHA only if the batch fails), then sequential `merge-tree` per PR. No "already have it?" pre-check: `cat-file -e` on a missing commit lazily fetches it one at a time. ripgrep (79 PRs): 9.8 s cold (35 lazy blob fetches by merge-tree), 0.9 s warm | Fetching by SHA keeps the check on exactly the head the API returned, even if the PR is pushed mid-scan; objects only, so `--repo-path` checkouts get no refs, config, or working-tree changes | Fetch `refs/pull/N/head` into local refs; prefetch the blobs merge-tree needs in one batch; parallel merge-tree with scoped threads |
| 2026-09-27 | PR verdicts combine as **superseded > abandoned > conflicts > ready_unreviewed > cant_tell**. | 2026-09-27 | PR `conflicts` = `git merge-tree --write-tree <head_sha> <pr_head>` exits 1; `high` (same ort merge GitHub uses). Evidence: one `code` item per conflicting file (first 10), ref = path, note names the last branch commit since the merge base touching it; the first note leads with "c of n changed files conflict (m of n changed on <branch> since the PR branched)". Only PRs whose base is the scanned branch; per-PR git errors (unfetchable head, unrelated history, shallow checkout) give no merge verdict and one warning line, never a failed scan | Matches the design example ("12 of 19 files changed on main"); `merge-tree` gives no line numbers | GitHub `mergeable` only (often UNKNOWN, and against the PR's base, not the scanned head) |
| 2026-09-27 | Incremental **skip rule**: only **LLM verdicts are reused**. An item copies the previous verdict/confidence/evidence/tier/`checked_at` when a previous item with the same kind + number has tier `llm` (including the LLM's `cant_tell`), an identical, complete fingerprint (`related_files` present), and this run's heuristics gave `cant_tell`. **Every heuristic always re-runs** (fetched data, git, code: references/reopens, PR activity, merge-tree, code-gone), and its result wins. Tier `none` (never checked) is never reused. `incremental::reusable()` is what the LLM check calls before calling the model. Prints `N reused, M re-checked (K new)`; with no LLM tier yet, reuse is 0 today | Heuristics are local and cheap (merge-tree ~7 s for 79 PRs), and some depend on the timeline or the clock; model calls are the cost the design worries about. Added `related_files` to the example PR item; `schema_version` stays 1 (additive) | Matches DESIGN "related files + blob SHAs"; no extra requests | Per-PR REST `/files` (one request per PR); record absent paths with a marker |
| 2026-09-27 | `--previous`: another repo → **error** (likely the wrong file); different `schema_version`, tool version, mode, or branch → warn and check everything; missing file → warn and check everything (the Action can always pass the gh-pages path); unparseable → error. | 2026-09-27 | PR thresholds are **configurable**: `PullThresholds { abandoned_after_days: 180, unreviewed_after_days: 21 }`, set by `scan --abandoned-after-days` / `--unreviewed-after-days`; planned `.stillvalid.yml` keys `pulls.abandoned_after_days` / `pulls.unreviewed_after_days` map onto the same struct. | 2026-09-27 | PR `abandoned` = no author activity for >= 180 days **and** checks FAILURE/ERROR or merge conflicts; inactivity alone stays `cant_tell`. High confidence at >= 365 days, else medium.
